# Terraform Project Structure — Best Practices

Source: [LinkedIn Post](https://www.linkedin.com/posts/alafonye-emmanuel_most-terraform-projects-fail-not-because-share-7451674800994848770-pa8b?utm_source=share&utm_medium=member_desktop&rcm=ACoAABluCTwB44tkeI2ie_AH9-HdTgMDEoJ5ys0)

## Overview

This structure organizes Terraform code into four logical layers to maximize scalability, reusability, and governance:

* **Environments** → Environment-specific configurations (dev, prod)
* **Modules** → Reusable infrastructure components
* **Policies** → Governance, compliance, and security rules
* **Scripts** → Automation for Terraform workflows

## 🌍 Environments Layer

### Purpose

Defines environment-specific infrastructure and orchestrates modules.

### Files

* **main.tf** → Calls modules with environment-specific configuration
* **variables.tf** → Declares variables used in the environment
* **outputs.tf** → Exports values for external use
* **terraform.tfvars** → Stores environment-specific variable values (avoid committing secrets)
* **backend.tf** → Configures remote state backend

### Rules

* One folder per environment (e.g., dev, prod)
* No hardcoded values
* Separate state per environment
* Keep configuration minimal; push logic into modules

---

## 🧩 Modules Layer

### Purpose

Reusable, composable infrastructure building blocks.

### Standard Structure

```
module-name/
├── main.tf        # Resource definitions
├── variables.tf   # Input variables
├── outputs.tf     # Exported values (IDs, ARNs, endpoints)
├── versions.tf    # Terraform and provider constraints
└── README.md      # Documentation and usage
```

### Guidelines

* Single responsibility per module
* No environment-specific logic
* Clearly defined inputs and outputs
* Version constraints must be explicit
* Document usage and examples in README

## 🛡️ Policies Layer

### Purpose

Implements governance, compliance, and security controls.

### Sentinel (Terraform Cloud/Enterprise)

* Cost control policies
* Security baselines
* Naming conventions

### OPA (Open Policy Agent)

* Tag validation rules
* Network security policies
* Compliance enforcement

### Structure

```
policies/
├── sentinel/
│   ├── cost-control.sentinel
│   ├── security-baseline.sentinel
│   └── naming-conventions.sentinel
└── opa/
    ├── resource-tagging.rego
    ├── network-rules.rego
    └── compliance.rego
```

## ⚙️ Scripts Layer

### Purpose

Standardizes and automates Terraform operations.

### Scripts

* **init.sh** → Initialize Terraform and backend
* **plan.sh** → Generate execution plan for review
* **apply.sh** → Apply infrastructure changes safely
* **destroy.sh** → Tear down infrastructure
* **validate.sh** → Format, lint, and validate configurations

### Example Workflow

```
./scripts/init.sh
./scripts/validate.sh
./scripts/plan.sh
./scripts/apply.sh
```

## ✅ Best Practices

### State Management

* Use remote backends (S3, Azure Blob, GCS)
* Enable state locking

### Versioning

* Pin Terraform version
* Pin provider versions

### Modularity

* Reuse modules across environments
* Avoid code duplication

### Isolation

* Maintain separate state per environment

### Secrets Management

* Use Vault, AWS SSM, or similar
* Never hardcode secrets

### Naming

* Enforce consistent naming conventions

### Tagging

Include standard tags:

* Environment
* Owner
* Cost Center

### Documentation

* Maintain README files for modules and root usage

### Backups

* Enable state versioning and backups

### Plan First

* Always review `terraform plan` output before applying

### Least Privilege

* Grant minimal IAM permissions required

## 🔁 Workflow Summary

1. Develop or update modules
2. Configure environment-specific inputs
3. Run validation scripts
4. Generate execution plan
5. Review changes
6. Apply infrastructure
7. Monitor outputs and state

## 📌 Key Principles

* Separation of concerns
* Reusability and modularity
* Security-first approach
* Automation-friendly design
* Environment isolation
